先理解四条主线

应用的工作可以还原成四条可组合流程：规则保存改变 Room 状态；AlarmScheduler 维持一个下一次开始闹钟；AppContainer 按域解析并应用壁纸；Android 和 UI 事件决定何时调用前述流程。

规则保存

授权图片 → 验证区间 → 重读冲突 → 写库 → 重排 → 立即应用。

调度循环

取消旧闹钟 → 计算最近开始 → 精确或降级注册 → 到点 → 应用 → 再排。

壁纸应用

读取规则快照 → 依次处理 LOCK/SYSTEM → 无命中保持 → 有命中解码和设置。

事件入口

启动、保存、删除、开机、包更新、授权获批、闹钟、亮屏和手动立即应用。

最容易误读的事实：规则结束时间本身不会触发“恢复”动作。应用只在下一条规则开始时切换；没有新规则时继续保持设备已有壁纸。

新建或编辑规则时发生什么？

即时 UI 校验只用于反馈；真正保存前会重新读取数据库区间再判断，避免依赖进入页面时的陈旧 occupiedIntervals。数据库仍没有跨行约束，所以这不是并发事务级保证。

未保存授权：选图成功就已经取得持久 URI 读授权。如果随后取消、校验/冲突失败，或再次选择另一张图，当前实现不会自动回收此前未被规则引用的授权；这是已知缺口，不要误以为“没有写库”就没有副作用。

为什么系统中只需要一个闹钟？

每次重排都从“所有合法且有图规则的开始分钟”计算最近下一次发生时间。闹钟到点后接收器再次重排，因此形成每日链式循环，而不是一次注册 1441 个候选 PendingIntent。计算使用设备当前本地日历时间。

一次“应用当前壁纸”怎样处理两个域？

双域入口只读取一次规则和当前分钟，然后依次处理 LOCK、SYSTEM。单域亮屏补偿直接进入同一个域处理器。无命中、无 URI、退避中或解码失败都属于“保持当前壁纸”的安全出口。

不同事件如何进入共享流程？

入口差异主要在“是否排程”“应用双域还是单域”“是否立即应用”。这些路径共享处理器，但并不继承完全相同的上游检查。

为什么图中没有首页 onResume：它不是独立系统 Receiver。首页恢复前台时会刷新当前规则、精确能力和电池白名单；只有精确能力从 ViewModel 记录的 false 变为 true 时才重排，true 变 false 不会立即替换既有闹钟。

如何解释“跳过、失败和完成”？

结果含义是否改壁纸是否影响下一域/下一次排程
无命中规则正常空档，保持已有壁纸否不阻止另一域；闹钟流程仍会重排
命中规则无 URI兼容 schema 可空的防御性跳过否不阻止另一域
LOCK 退避中避免每次亮屏重复调用已失败的厂商实现否30 分钟后或进程重启后可再试
图片解码失败URI 不可读、格式问题或 decode 返回 null否记录日志；另一域继续
WallpaperManager 失败系统/厂商拒绝或抛异常未成功LOCK 设置退避；SYSTEM 只记录；另一域继续
保存链后半段异常可能已经写库或重排，但 UI 仍提示“保存失败”；没有跨步骤回滚取决于失败步骤重新进入页面应以 Room 实际数据为准
重排异常旧固定闹钟已经先取消，读库或注册失败时可能暂时没有下一次闹钟否等待下一个重排入口；当前没有自动重试
闹钟处理意外抛异常applyCurrentNow 若向外抛出，后面的 rescheduleNext 不保证执行可能部分完成调度闭环可能中断，需靠其它入口恢复
Receiver 正常 finish异步处理生命周期结束不代表成功业务结果必须看各域日志
用户强制停止系统阻断闹钟和广播否无法自动恢复，必须重新打开应用
时间恢复缺口：当前没有 TIME_SET、TIMEZONE_CHANGED 或日期变化入口。用户手动改钟、跨时区或遇到夏令时后，要等启动、保存、删除、授权变化或既有闹钟等其它入口重排；细节见架构限制表。

修改流程后怎样验证？

纯逻辑

运行 19 个 JVM 测试，重点覆盖 resolve 边界、分域、startMinutes、范围与 24:00 解析。

静态与构建

运行 :app:lintDebug :app:assembleDebug，并检查 Manifest Receiver 与权限。

调度真机

验证相邻规则交接、空档保持、授权前后、重启、覆盖安装与强停后重开。

壁纸真机

分别验证 LOCK/SYSTEM、同时间跨域、URI 替换/删除，以及受限 ROM 的锁屏失败恢复。

第三方修改原则：新增任何规则写入口，都必须同时维护范围、同域冲突、URI 授权、重排和即时应用语义；新增任何系统触发入口，都应优先复用 AppContainer/AlarmScheduler，而不是复制 resolve 或 WallpaperManager 调用。
