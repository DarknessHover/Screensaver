从一个屏保项目出发：
MVVM 与跨端架构的通用思维

以 Screensaver（Android · Kotlin · Compose）为活体标本，对照 MVC 讲清 MVVM，
再把同一套思想平移到前端与后端。

2026-09-01 编排 案例项目：Screensaver · 定时壁纸 技术栈：Kotlin 1.9.24 · Compose M3 · StateFlow · Room 读者基线：熟悉 MVC，初学 MVVM
本教材想回答两个问题。第一讲：MVVM 到底在解决什么——答案藏在 MVC 的四个病灶里，而不是藏在定义里。 第二讲：这套思想能不能带出移动端——答案是它早就在 Web 和后端住了二十年，只是换了名字； 真正需要你新学的东西，只有"Web 比移动端多出来的那两层"。
序 · PROLOGUE

一个小项目，为什么能装下这么多东西

架构思想的价值不在项目大小，而在于"每一层是否都被真实需求逼出来过"。这个 3000 行量级的屏保项目，恰好每一层都逼出过一次。

你的 Screensaver 项目规模很小：一个首页、一个编辑器、一个数据库、几个系统 Receiver。但在这两讲里，我们会从它身上抽出四条可以带走的通用能力：

  1. 看懂一个架构在解什么题不再背"MVVM 是 Model-View-ViewModel"，而是问"它把 MVC 的哪个病灶切掉了"。学会这一条，以后遇到任何新架构都能自己拆解。
  2. 判断一段代码该放哪一层这是架构落到日常开发里唯一真正的动作。分辨得出"这是纯计算 / 这是状态 / 这是系统能力 / 这是一帧的临时显示"，代码就不会烂。
  3. 把一套分层直觉跨端复用Android、Web 前端、FastAPI 后端，看起来是三个世界，其实是同一张分层图换了三套名词。
  4. 识别"范式收敛"的信号2026 年 Signals 在全行业收敛，是一次典型的范式级变化。能识别它，就能判断什么时候该跟进、什么时候该按兵不动。

第一讲 · CHAPTER Ⅰ

MVC 到底哪里疼

先别急着学 MVVM 的定义。任何架构都是"止痛药"，你得先知道痛在哪，才知道那一刀为什么切在那里。

1.1 MVC 只规定了三件事，但没规定它们住哪

MVC 的划分其实非常朴素：Model 是数据，View 是显示，Controller 是把用户动作翻译成数据操作的那段胶水。问题在于——它只说了"有三个角色"，没说"这三个角色是否应该是三个对象"。

在 Android 上，这个模糊被放大成了灾难：Activity 天生既是 View（它持有 setContentView 出来的那棵树），又是最自然的 Controller 落点（所有点击回调都注册在它身上）。于是它同时是三个角色。

1.2 四个病灶，两端一模一样

表 1-1　MVC 的四个病灶，在移动端与 Web 上的同构表现

上帝类 Activity 里既有 findViewById 又有 onClick 又有数据库查询，轻松 2000 行 jQuery 时代 $('#btn').click() 里既改 DOM 又发请求 又算业务 View 与 Controller
没有物理边界
状态易失 旋转屏幕 → Activity 重建 → 成员变量全没 刷新页面 → JS 上下文重建 → 状态全没 状态寄存在
"会死的东西"上
不可单测 要测业务逻辑，得跑 instrumentation test 起模拟器 要测业务逻辑，得开浏览器 + 造 DOM 环境 逻辑与渲染

四个病灶的共同根因

状态被放在了一个"既会死、又还要负责画画"的对象上。因为它会死，所以状态不安全；因为它在画画，所以逻辑没法脱离界面测试；因为两者混在一起，所以同步只能靠人记。

MVVM 的解法说穿了就一句：把状态从这个对象里搬走，搬到一个不会随界面销毁而消失的地方。剩下的所有设计（单向数据流、声明式 UI、状态容器）都是为了服务这一件事。

顺带澄清一个常见误解

"MVVM" 这个词在 Web 上出现得比 Android 更早——AngularJS（2010 年）当年官网直接写的就是 MVVM。后来前端进入组件化时代，"ViewModel" 这个词指代不清了，社区才改叫状态管理（State Management）。名字会过时，思想不会。以后遇到陌生架构术语，先问"它在解 MVC 的哪个病灶"，比背定义快十倍。

第一讲 · CHAPTER Ⅰ

MVVM：把状态从"会死的东西"里搬出来

ViewModel 不是一个"放代码的文件夹"，它是一个有明确职责的、活得更久的状态宿主。这一章我们拿 Screensaver 的真实代码逐段对照。

这里有个容易忽略的关键点：ViewModel 之所以能"活得更久"，不是因为它特殊，而是因为它被一个更外层的容器托着。Android 里这个容器叫 ViewModelStore——屏幕旋转时 Activity 销毁重建，但 ViewModelStore 挂在"这次任务"上而不是"这个 Activity 实例"上，所以 ViewModel 活下来了；只有当 Activity 真正 finish()（用户彻底退出）时它才被清理。

2.2 单向数据流：把网状箭头拉成两条

MVC 的箭头是网状的（谁都能改谁），MVVM 把它压成两条方向固定的通道。这就是单向数据流（Unidirectional Data Flow, UDF）。

对应到你的代码，这条链路就是：

app/src/main/java/com/screensaver/ui/screens/HomeScreen.kt KOTLIN 
// ③ 状态流回：collect 把 StateFlow 接到 Compose，值一变自动重组
val filteredRules     by vm.filteredRules.collectAsStateWithLifecycle()
val currentRuleForTab by vm.currentRuleForTab.collectAsStateWithLifecycle()
val selectedTab       by vm.selectedTab.collectAsStateWithLifecycle()

// ① 事件上报：View 不自己算，只把"用户点了哪个 Tab"告诉 ViewModel
DomainSegmentedTabs(
    selected = selectedTab,
    onSelect = vm::selectTab,          // 注意：传的是函数引用，不是把状态丢出去改
)
…/ui/viewmodel/HomeViewModel.kt KOTLIN 
/** 顶部域切换器当前所选项（默认屏保）。 */
private val _selectedTab = MutableStateFlow(WallpaperDomain.LOCK)
val selectedTab: StateFlow<WallpaperDomain> = _selectedTab   // 对外只读

// ② 写入新状态：唯一的修改入口，且写的是"新值"而不是"改字段"
fun selectTab(tab: WallpaperDomain) {
    if (_selectedTab.value != tab) _selectedTab.value = tab
}
为什么非要 "_xxx 私有 + xxx 只读" 这套啰嗦写法

这不是 Kotlin 的繁文缛节，而是把"修改权"变成一种编译期可检查的约束：MutableStateFlow 留在 ViewModel 内部，外面拿到的 StateFlow 没有 .value 的 setter。View 层就算想违规改状态，IDE 直接报红。
架构约束一旦只靠"约定"，就一定会有人破例；能下沉到编译器检查的，才是真约束。

2.3 状态容器三要素：为什么偏偏是 StateFlow

把状态搬出来了，得找个容器装。StateFlow 能胜任，靠的是三个恰好都踩在需求上的特性：

派生状态：能算出来的，就不要存

你的首页有个典型场景："当前选中的域" + "全部规则" → "该域的规则列表"。这个列表是派生出来的，不该再存一份——存了就要同时维护两份，早晚不一致。

…/ui/viewmodel/HomeViewModel.kt　（派生状态与订阅共享） KOTLIN 
// 源状态：DB 流 → 转成 StateFlow，多个订阅者共享同一条上游（只查一次库）
private val rules: StateFlow<List<ScheduleRuleEntity>> = repository.observeRules()
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), emptyList())

// 派生状态：过滤 + 排序，不落库、不缓存，随源变化自动重算
val filteredRules: StateFlow<List<ScheduleRuleEntity>> =
    combine(rules, _selectedTab) { all, tab ->
        all.asSequence()
            .filter { it.wallpaperDomain == tab }
            .sortedBy { it.startMinute }
            .toList()
    }.stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), emptyList())
WhileSubscribed(5000) 里的 5000 是什么

它的含义是：最后一个订阅者消失后，再等 5 秒才停掉上游流。这个"宽限期"是为屏幕旋转准备的——旋转时旧的 Composable 销毁（订阅者归零）、新的立刻重建（订阅者回来），中间通常不到 1 秒。如果宽限期是 0，每次旋转都会真的断开数据库流再重连，白白浪费一次查询。
判断标准：这个数值应该略大于"界面销毁到重建"的耗时。

2.4 两个真实的坑（都写在你的代码里）

坑一：一次性事件放进 StateFlow，会重放

"保存成功"这种提示，是一次性事件——它不是一个"持续为真的状态"。如果把它塞进 StateFlow：屏幕一旋转，Composable 重建并重新 collect，那个值还在，于是 Toast 又弹了一遍。

错误 事件当成状态存

把提示塞进 UiState 的一个字段，界面重建时它还在 → 提示重复弹出；而且"提示"这个东西在业务上根本不是状态。

正解 双通道：状态 + 事件

状态走 StateFlow（可重放，本来就该重放）；一次性事件走 SharedFlow（发出即消费，不留存）。

…/ui/viewmodel/RuleEditorViewModel.kt　（双通道：状态流 + 事件流） KOTLIN 
// 通道 A：持续状态 —— 界面重建后要原样恢复，所以可重放
private val _state = MutableStateFlow(RuleEditorState())
val state: StateFlow<RuleEditorState> = _state

// 通道 B：一次性提示事件（成功/冲突/失败原因），由界面弹 Snackbar
// extraBufferCapacity=4：允许在无人订阅时先攒着，避免 emit 挂起丢失
private val _events = MutableSharedFlow<String>(extraBufferCapacity = 4)
val events: SharedFlow<String> = _events

// 使用处：校验不通过时发事件，而不是改状态
val conflict = findConflict(s.startMinute, s.endMinute)
if (conflict != null) {
    _events.tryEmit(conflict)   // 注意用 tryEmit，不挂起、不丢事件
    return@launch
}
if (s.selectedImageUri == null) {
    _events.tryEmit("请先为规则选择一张素材图片")
    return@launch
}

坑二：ViewModel 感知不到 ON_RESUME

ViewModel 的生命周期比 View 长，这是优点；但代价是——它对"界面重新回到前台"这件事一无所知。它只有 onCleared()，没有 onResume()。

你的项目里正好踩到了这个坑，而且解法就写在 HomeScreen.kt 里，注释写得非常清楚：

…/ui/screens/HomeScreen.kt　（由 View 把生命周期事件通知给 ViewModel） KOTLIN 
val lifecycleOwner = LocalLifecycleOwner.current
DisposableEffect(lifecycleOwner) {
    val observer = LifecycleEventObserver { _, event ->
        if (event == Lifecycle.Event.ON_RESUME) {
            vm.refreshExactAlarmStatus()
            // 暖启动（从最近任务/点图标恢复）不走 onCreate，
            // 必须在此重算"当前生效规则"，否则 Hero/生效中标签停留在上次前台时刻的旧状态
            vm.recomputeCurrent()
        }
    }
    lifecycleOwner.lifecycle.addObserver(observer)
    onDispose { lifecycleOwner.lifecycle.removeObserver(observer) }
}
这个坑的通用形态

凡是"从系统设置页返回""从别的 App 切回来"这类场景，ViewModel 都需要被通知。通用解法：由 View 侧用生命周期观察者把事件转发给 ViewModel。 DisposableEffect 的 onDispose 负责注销——忘了注销就是内存泄漏，这一对必须成对出现。

3.1 实例解剖：为什么 ScheduleEngine 是 object 而不是 class

app/src/main/java/com/screensaver/domain/scheduler/ScheduleEngine.kt KOTLIN 
/**
 * 调度引擎：纯函数，无 Android 运行时时依赖（操作的是纯 Kotlin 实体），便于单测。
 *
 * 模型（对齐需求/架构文档的"剪开拉直"）：
 *  - 一天 = 0:00 → 24:00 的一条直线，被切成 0..1439 的"当天第几分钟"。
 *  - 一条规则永远不跨午夜（跨午夜由编辑器拆成两条存储），故 endMinute 永远 > startMinute。
 *  - 因此命中判断只有【一种】：start <= now < end，无需任何 wrap-around 分支。
 */
object ScheduleEngine {          // ← object：无状态，天然单例，不需要注入

    fun resolve(
        now: Int,
        rules: List<ScheduleRuleEntity>,
        domain: WallpaperDomain,
    ): ScheduleRuleEntity? {
        return rules.filter {
            it.wallpaperDomain == domain &&
                it.startMinute <= now && now < it.endMinute
        }.minByOrNull { it.startMinute }
    }
}

这段代码里藏着三个可以立刻复用的设计决策：

  1. 用 object 而不是 class无状态的工具用 object，省掉一次依赖注入。判断标准：如果它不需要被替换成假实现来测试，就不必做成可注入的类。
  2. 用"剪开拉直"消灭分支把"一天"建模成一条 0..1439 的直线，规定规则不跨午夜（跨午夜由编辑器拆成两条存储）。于是命中判断只剩下 start <= now < end 一种情况，不需要任何跨午夜的 wrap-around 分支。
    这是数据建模的威力：约束加在存储层，逻辑层就干净了。
  3. 返回 null 而不是"默认规则"注释写得很明确："若无命中的规则则返回 null —— 调用方据此不干预，保持该域已有壁纸"。用 null 表达"无"这个业务语义，比用哨兵值安全得多。
记住这句话

"能算出来的就不要存，能约束在存储层的就不要留给逻辑层。"你在 Screensaver 里反复做的这两件事（派生状态用 combine、跨午夜在编辑器拆条），就是架构思维的具体形态。

4.2 关键洞察：你学的是"两套响应式"，只是没人这么告诉你

这是本讲最重要的一层抽象，也是理解 2026 年前端格局的钥匙。你在 Screensaver 里其实已经接触了两套机制完全不同的响应式，只是它们长得像，没人给你拆开讲：

粗粒度 StateFlow —— 状态容器

需要显式 collect 才能拿到变化；跨组件、跨层共享；有初值；只存最新；equals 去重。

订阅关系是"你写了才算"，粒度是整个对象。

细粒度 mutableStateOf —— 信号

不用订阅，谁读它谁就自动被登记为依赖；它变了，只重算真正读过它的那一小块。

依赖图是运行时自动长出来的，粒度是单个值。

这一层抽象能帮你省掉多少事

想通了这张图，以后看到任何 Web 框架的新名词，你只需要问两个问题：
① 它属于上层（共享状态容器）还是下层（细粒度信号）？
② 它的"桥"长什么样（怎么把上层接到渲染）？
答完这两个问题，剩下的都是语法差异。Pinia 就是 StateFlow 的亲戚，ref() 就是 mutableStateOf 的亲戚——不需要重新学一遍概念。

4.3 Web 比移动端多出来的两层

如果你直接把 Android MVVM 平移到 Web，会漏掉两块。而这两块，恰恰是前端架构近五年最主要的演进方向。

多出来的一层：服务端状态（Server State）

移动端也有网络数据，但 Web 的数据获取场景重得多（分页、轮询、竞态、乐观更新、缓存失效）。社区早年的教训是把服务端数据塞进 store，结果每个页面都要手写 loading / error / 重试 / 缓存 / 失效那一整套。

多出来的另一"层"：URL 也是状态

Web 的路由是可分享、可回退、可收藏的。所以"当前在哪一屏""筛选条件是什么"这类状态，在 Web 侧的正确归属经常是 URL 参数而不是 store。

有意思的是——你今天刚修的那个 bug，用的就是同一个思路：

…/ui/MainActivity.kt　（把"当前在哪个域"编码进路由，跨界面传递状态） KOTLIN 
composable(
    route = "editor/{ruleId}?domain={domain}",      // ← 状态编码进路由
    arguments = listOf(
        navArgument("ruleId") { type = NavType.LongType; defaultValue = -1L },
        navArgument("domain") {
            type = NavType.StringType
            defaultValue = WallpaperDomain.SYSTEM.name    // 缺省值保证旧路由仍可匹配
        }
    ),
) { backStack ->
    val id = backStack.arguments?.getLong("ruleId")?.takeIf { it >= 0L }
    // 新建规则的预选域（继承首页当前 Tab）；编辑已有规则时忽略此参数
    val domain = backStack.arguments
        ?.getString("domain")
        ?.let { d -> runCatching { WallpaperDomain.valueOf(d) }.getOrNull() }
        ?: WallpaperDomain.SYSTEM
    RuleEditorScreen(nav, id, domain, viewModel<RuleEditorViewModel>(factory = factory))
}
可复用的工程细节

注意 runCatching { valueOf(d) }.getOrNull() 这一手：从外部传入的枚举字符串一律要兜底。路由参数可能来自旧版本的 deep link、手写的 adb 命令、甚至未来的自己。valueOf 遇到非法值会直接抛异常导致崩溃，加一层兜底就变成了"回退到默认值"。
这类"边界防御"是中级和初级的分水岭之一。

为什么"会一层就能触类旁通"？因为这些分层不是某个框架的发明，而是对同一类复杂度的同一种收敛：
① 把变化频繁的（UI / 协议）关在最外层；
② 把稳定的（业务规则）放在中间；
③ 把不可控的（DB / 网络 / 系统）关在最内层并加门面。
无论前端后端移动端，只要复杂度长这样，分层就长这样。

6.3 标准化进度：不要在生产上建在提案上

TC39 Signals 提案的真实状态（截至 2026-08）

仍是 Stage 1。2024 年 4 月进入 Stage 1，此后两年多未申请进入 Stage 2；提案仓库主分支最后一次提交停留在 2025-08；参考实现 signal-polyfill 停在 0.2.2（2025-01）。没有任何 JS 引擎原生实现它。

API 面只有三个东西：Signal.State（可写单元）、Signal.Computed（惰性记忆化派生）、Signal.subtle.Watcher（给框架用的底层钩子）。
故意不包含 effect() —— 调度、批处理、渲染集成全部留给框架。理由很漂亮：语言拥有依赖图，框架拥有调度策略。

结论：把它当作"行业对答案形状达成了一致"的验证，而不是"今年就能用上的东西"。生产代码请写框架自带的成熟实现。

6.4 React 为什么说不：一个值得收藏的架构权衡案例

React 是全球最大的前端生态，它偏偏没跟 Signals。这不是落后，是一次公开论证过的、有意识的取舍。

React 的立场大致是："React 本身就是 signals 所解决的那个问题的解决方案。"
在 React 之前，细粒度响应式（Knockout、早期 Angular）意味着手工接线哪个依赖哪个，bug 就住在接线里。React 的主张是：别管依赖了，把 UI 描述成状态的函数，让框架去算更新。
而在 Signals 模型里，你必须预先决定什么是 state、什么是 derived、什么是 effect，还得把代码从内到外地组织起来才能保住那张依赖图。 —— 社区对 React 团队（Dan Abramov 等）公开论证的转述，非原文引用
Signals 阵营 显式依赖图

优点：更新精确到值，无需 memo/依赖数组，没有闭包过期问题。

代价：开发者要预先分类状态，且在条件分支里声明信号时语义会变模糊。

React 阵营 一切默认响应式

优点：心智模型简单，"computed"只是可选优化而非必须。

代价：需要 Compiler 在编译期补 memo 来追平性能；运行时仍落后约 30%。

架构师视角：这不是技术之争，是"存量资产"之争

React 有全世界最大的存量代码库。改心智模型 = 让 2000 万开发者重写一遍脑子，这个代价它付不起。所以宁可用编译器去逼近 Signals 的性能，也要保住 API 兼容。
判断这类问题时，永远先问"改这个决定的迁移成本由谁承担"。技术优越性在迁移成本面前经常不是决定性因素——这一条对你以后做技术选型非常有用。

6.6 行业共识：真正的收益是可维护性，不是性能

Signals 消灭的不是渲染开销，而是 memo / useMemo / useCallback / 依赖数组 / 闭包过期这一整类复杂度。那些东西的本质是手工维护依赖图，而 Signals 让依赖图自动长出来。 —— 多篇 2026 年前端展望的共同结论

因此社区给出的一致性建议是：

  1. 新项目首选 signals 系迁移成本为零，直接享受心智负担的下降。
  2. 老项目"必须迁移"几乎从不是路线图上最高价值的事尤其是已经在跑、能赚钱的项目。把架构纯粹性排在真实 bug 前面，通常是个错误。
  3. 选型随场景分化内容站 / 全栈 → Next.js（RSC）；中后台 → Vue + Nuxt（遇到性能瓶颈再开 Vapor）；高交互实时仪表盘 → Solid 或 Svelte。元框架（Next / Nuxt / SvelteKit / Astro）已成为新建项目的默认起点。

可带走的三条思想，与三条忠告

如果这份教材你只记住一页，就记这一页。

可带走的三条思想

  1. 状态应该活得比 UI 久，且不该由 UI 持有这是 MVVM、Flux、Signals、乃至服务端 session 设计的共同底层逻辑。凡是"刷新一下就没了但你希望它还在"的东西，都属于这一层。这条能迁移到任何端、任何框架。
  2. 依赖方向要单向，且越界的代价要尽量高单向数据流不是为了好看，是为了让"当前界面对不对"变成一个可推理的纯函数。能下沉到编译器检查的约束（如 StateFlow 对外只读）才是真约束。
  3. 能算的别存，能约束在存储层的别留给逻辑层派生状态用 combine；跨午夜在编辑器拆成两条而不是在引擎里写 wrap-around 分支。把复杂度前移到数据模型，后面的代码会成片地变简单。

三条忠告

一 · 一套学透，别追名词

Pinia、Zustand、Signals、Runes 看着五花八门，落到你的心智里就一句："状态从 UI 里挪出来，UI 订阅状态"。剩下的都是语法差异。追新名词而基础不牢，是初级到中级最常见的消耗陷阱。

二 · 判断架构好坏的尺子只有一把

改一个需求，要动几个地方？
今天那个"屏保 Tab 新建、默认域却是桌面"的 bug，本质就是状态归属没想清楚——首页的"当前 Tab"这个状态没有打通到编辑器，只能在层与层之间用参数硬传。这类 bug 在 Web 里同样是最高频的一类。
所以：动手画"状态归属表"的时间，永远是值得的。

三 · 别急着重写老项目

行业对 Signals 的主流建议就是"新项目用、老项目不急"。你的 Screensaver 已经能跑——为架构纯粹性去返工，性价比通常低于修掉一个真实 bug。
例外只有一种：当架构问题已经在持续产生 bug 时，它就不是纯粹性问题，而是成本问题了。

术语速查与代码索引

术语速查

MVC
Model / View / Controller。只规定角色，不规定物理边界——这是它所有问题的源头。
MVVM
Model / View / ViewModel。核心增量是 ViewModel 这个"活得比 View 久的状态宿主"。
UDF（单向数据流）
事件向上、状态向下，方向不可逆。可预测性的来源。
StateFlow
有初值 / 只留最新 / equals 去重的粗粒度状态容器，需显式 collect。
SharedFlow
不留存历史的一次性事件通道，用于 Toast / 导航 / 提示。
Signal（信号）
细粒度响应式单元：读即订阅，依赖图自动生成。Web 侧的正名运动，2026 年完成收敛。
store
Web 侧的跨组件共享状态容器，等价于 Android 的 ViewModel + StateFlow。
Server State
所有权在远端、会过期的数据。与 Client State 分开管理，是现代前端架构的关键分野。
派生状态
由其他状态算出来的状态，不落库、不缓存，随源自动重算（combine）。
TC39
负责 ECMAScript 标准的技术委员会。Stage 1 = 官方开始讨论，远未定型。
RSC
React Server Components，把组件与数据获取搬到服务端，客户端包体积显著下降。
元框架
Next / Nuxt / SvelteKit / Astro 等"框架之上的框架"，2026 年已成新建项目默认起点。
