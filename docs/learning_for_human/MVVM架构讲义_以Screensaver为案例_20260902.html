MVVM 架构讲义 · FOCUSED EDITION

把状态从"会死的东西"
搬到活得下去的地方

以 Screensaver（Android · Kotlin · Compose）为唯一案例，
从"为什么需要 MVVM"讲到"代码该放哪一层"，只讲这一条主线。

2026-09-02 编排 案例项目：Screensaver · 定时壁纸 技术栈：Kotlin · Compose M3 · StateFlow · Room 读者基线：熟悉 MVC，初学 MVVM
本讲义只回答一个问题：一段代码，该放在哪里？
为了答好它，我们需要先拆掉一个流行误解（架构 ≠ 分包），再理解 MVC 到底哪里疼， 然后看 MVVM 怎么一层一层地解开它，最后落到"状态传导的三种机制"和"目录怎么建"这两个每天都在用的动作上。
第零章 · PREREQUISITE

前提：架构不是分包

这一章不教 MVVM，它负责拆掉一个几乎所有初学者都有、且会一直阻碍你理解架构的误解。跳过它，后面每一章都会学歪。

0.1 一个听起来很对、实际很危险的定义

"架构就是……将不同功能的代码放在不同的包中，让项目路径更加清爽，一目了然。"

这个定义的每一半都很讨喜：它具体、可操作、看得见摸得着。所以几乎所有人都会先接受它。

问题在于：它描述的是架构带来的"副作用"，不是架构本身。把结果当成定义，你会得到一个非常糟糕的后果——

后果

你会开始用"目录好不好看"来评价架构好坏。于是你会花时间调整包的名字和层级，却对真正致命的东西（谁 import 了谁）视而不见。
更糟的是：你会觉得"我项目结构挺规范的，架构应该没问题"——而此时架构可能已经烂透了。

0.2 三个论证，拆掉这个定义

论证一｜同样的包结构，可以长出完全违反架构的代码

假设你的项目保持现在的 ui/、data/、domain/ 三包不动，我在界面文件里加两行：

反例：ui/screens/HomeScreen.kt（虚构，请勿模仿） KOTLIN 
import com.screensaver.data.local.AppDatabase   // ← View 直接摸数据库

@Composable
fun HomeScreen(...) {
    val db = AppDatabase.get(LocalContext.current)
    val rules = db.ruleDao().getAll().collectAsState(initial = emptyList())
    // 界面里直接查库、直接算业务——目录一个字没改
}

目录还是那么清爽，三个包的名字一个没动，但架构已经死透了：业务逻辑再也脱离不了界面测试，改一个数据库字段要动 UI，屏幕旋转还可能泄漏 Context。

论证二｜不同的包结构，可以是同一个架构

按层分
ui/screens/     HomeScreen
ui/viewmodel/   HomeViewModel
domain/         ScheduleEngine

按功能分
feature/home/   HomeScreen

两种包结构完全不同，但架构完全一样。如果架构 = 分包，这就是两个架构了——显然不是。

论证三｜架构真正的三条约束，没有一条跟"路径"有关

表 0-1　架构的三条真约束
约束它问的问题违反时的症状
依赖方向这个包允许 import 谁？禁止被谁 import？循环依赖；改一处崩一片；无法单独复用某个模块

一句话记住

「这个包能 import 什么、不能被谁 import」才是架构；「这个包叫什么名字」只是目录。
目录是约束的投影。你盯着投影看，永远学不会架构。

你的项目里恰好有一个绝佳的实例。我列包结构时发现——你有两个都叫 scheduler 的包：

按"路径清爽"的标准，这是脏的——两个同名包，早该合并。但它在架构上完全正确。看它们的 import 就知道为什么：

这一条怎么用在你的日常里

判断一个目录划分对不对，问一句就够："这个目录允许 import 什么？" 答不上来 → 这个目录只是个文件夹，不是架构的一部分。
反过来说：如果哪天有人给 ScheduleEngine 加了一行 import android.util.Log，它就该立刻被移出 domain/——哪怕业务逻辑一行没改，架构也已经坏了。

0.4 顺带纠正：你学的"MVC"其实是个混血

你之前这样描述 MVC："Model 封装业务逻辑与数据访问（Service 调 DAO，DAO 管增删改查）"。

这里塞了不属于 MVC 的东西。经典 MVC 是表现层内部的组织方式，它的 Model 是"数据 + 业务逻辑"，里面没有 Service 和 DAO 的位置。你说的 Service → DAO 是三层架构的东西。

表 0-2　两个被混为一谈的东西
经典 MVC三层架构真实项目（Spring / FastAPI）
管什么表现层内部怎么组织整个应用纵向分几层两者叠加
组成部分View / Controller / Model表现层 → 业务层 → 数据层表现层里用 MVC 的命名，下面照三层来
"Model"是啥数据 + 业务逻辑—退化成传给视图的数据载体（ModelAndView 里的那个 Model）
Service/DAO 在哪不在 MVC 里业务层 / 数据层在 MVC 的下面，不在 MVC 的"Model"里
分清之后你能得到什么

你手里其实有两把尺子，别只用一把：
① 分层管纵向深度（表现 → 业务 → 数据）——几乎任何项目都需要，无论你用什么 XVM；
② MVC / MVVM 管表现层内部怎么组织——只有界面复杂到一定程度才需要。
它们是正交的。混淆这两把尺子，是很多人学架构时越学越乱的根源。

第一章 · CHAPTER Ⅰ

MVC 的四个病灶

架构是止痛药。不知道痛在哪，就不知道那一刀为什么切在那里。

1.1 MVC 只规定了角色，没规定它们住哪

MVC 的划分很朴素：Model 是数据，View 是显示，Controller 是把用户动作翻译成数据操作的胶水。问题是——它只说"有三个角色"，没说"这三个角色是否应该是三个对象"。

在 Android 上，这个模糊被放大成灾难：Activity 天生既是 View（持有 setContentView 出来的那棵树），又是最自然的 Controller 落点（所有点击回调都注册在它身上）。于是它同时是三个角色。

1.2 四个病灶

表 1-1　MVC 的四个病灶与共同根因
病灶表现根因
上帝类Activity 里既有 findViewById 又有 onClick 又有数据库查询，轻松 2000 行View 与 Controller 无物理边界
状态易失旋转屏幕 → Activity 重建 → 成员变量全没状态寄存在"会死的东西"上
不可单测要测业务逻辑，得起模拟器跑 instrumentation test逻辑与渲染耦合在同一对象
同步靠人肉改完数据要记得 textView.text = ...，漏一处就显示陈旧值状态→UI 的映射由人工维护
四个病灶的共同根因

状态被放在了一个"既会死、又还要负责画画"的对象上。
因为它会死 → 状态不安全；因为它在画画 → 逻辑没法脱离界面测试；因为两者混在一起 → 同步只能靠人记。

MVVM 的解法说穿了就一句：把状态从这个对象里搬走，搬到一个不会随界面销毁而消失的地方。后面所有设计（单向数据流、状态容器、数据绑定）都只为服务这一件事。

1.3 分水岭：谁来触发界面更新

这是从 MVC 跨到 MVVM 真正的门槛，也是最容易被一句话带过的地方。

MVC 的定义里有一句："Controller 调用 Model 处理，并选择合适的 View 渲染结果"。

这个"选择"的动作，在 MVVM 里被彻底消灭了。

看你的代码，这个区别非常具体：

…/ui/viewmodel/HomeViewModel.kt KOTLIN 
// ViewModel 只管改状态。注意：没有 notifyDataSetChanged()，没有 refreshUI()
fun selectTab(tab: WallpaperDomain) {
    if (_selectedTab.value != tab) _selectedTab.value = tab
    // ← 就这一行。谁在显示？几个地方在显示？ViewModel 不知道，也不需要知道
}
跨过这道坎的标志

当你不再问"它怎么知道该刷新了"，而是自然地认为"它读过了，所以它会被通知"——你就跨过去了。
这个"读过了就自动通知"的机制，就是第 4 章要讲的 Signals。你现在已经站在它的门口了。

第二章 · CHAPTER Ⅱ

MVVM 的解法

状态搬出来了，得有地方放、有规矩传、有办法不写错。这一章全是能直接用的东西。

2.1 三层各自的确权

表 2-1　MVVM 三层职责边界（以 Screensaver 为例）

View渲染状态、收集用户动作、持有"只影响这一帧"的临时 UI 状态直接读写数据库；自己算业务结论；长期持有数据HomeScreen

一个容易忽略的关键点：ViewModel 之所以"活得更久"，不是因为它特殊，而是因为它被一个更外层的容器托着——Android 里叫 ViewModelStore。屏幕旋转时 Activity 销毁重建，但 ViewModelStore 挂在"这次任务"上而不是"这个 Activity 实例"上，所以 ViewModel 活下来了；只有用户彻底退出（Activity 真正 finish()）时才清理。

2.2 单向数据流：把网状箭头拉成两条

…/ui/screens/HomeScreen.kt　（③ 订阅 与 ① 上报） KOTLIN 
// ③ 状态流回：collect 把 StateFlow 接到 Compose，值一变自动重组
val filteredRules     by vm.filteredRules.collectAsStateWithLifecycle()
val selectedTab       by vm.selectedTab.collectAsStateWithLifecycle()

// ① 事件上报：View 不自己算，只把"用户点了哪个 Tab"告诉 ViewModel
DomainSegmentedTabs(
    selected = selectedTab,
    onSelect = vm::selectTab,      // 传的是函数引用，不是把状态丢出去改
)
为什么非要 "_xxx 私有 + xxx 只读" 这套啰嗦写法

这不是 Kotlin 的繁文缛节，而是把"修改权"变成编译期可检查的约束： MutableStateFlow 留在 ViewModel 内部，外面拿到的 StateFlow 没有 .value 的 setter。View 层就算想违规改状态，IDE 直接报红。

架构约束一旦只靠"约定"，就一定会有人破例；能下沉到编译器检查的，才是真约束。——这正是第 0 章"依赖方向"在代码层面的落地。

2.3 状态容器三要素：为什么偏偏是 StateFlow

表 2-2　StateFlow 的三个特性，每一个都对应 UI 状态的一个刚需
特性含义为什么 UI 状态恰好需要它
必须有初值构造时就得给值：MutableStateFlow(LOCK)界面第一帧就得画点什么，不能"还没数据"。天然消灭 loading 空窗判断
只保留最新conflate 背压策略：连发 10 个值，旧 9 个丢弃UI 关心的永远是"现在是什么"，中间态没有意义
equals 去重写入相同值不通知下游data class 的结构化相等让"值没变"被自动识别，省掉无意义重组。这就是 RuleEditorState 必须是 data class 的真正原因

派生状态：能算出来的，就不要存

你的首页有典型场景："当前选中的域" + "全部规则" → "该域的规则列表"。这个列表是派生出来的，不该再存一份——存了就要同时维护两份，早晚不一致。

…/ui/viewmodel/HomeViewModel.kt　（派生状态与订阅共享） KOTLIN 
// 源状态：DB 流 → 转成 StateFlow，多个订阅者共享同一条上游（只查一次库）
private val rules: StateFlow<List<ScheduleRuleEntity>> = repository.observeRules()
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), emptyList())

// 派生状态：过滤 + 排序，不落库、不缓存，随源变化自动重算
val filteredRules: StateFlow<List<ScheduleRuleEntity>> =
    combine(rules, _selectedTab) { all, tab ->
        all.asSequence()
            .filter { it.wallpaperDomain == tab }
            .sortedBy { it.startMinute }
            .toList()
    }.stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), emptyList())
WhileSubscribed(5000) 里的 5000 是什么

它的含义是：最后一个订阅者消失后，再等 5 秒才停掉上游流。这个"宽限期"是为屏幕旋转准备的——旋转时旧 Composable 销毁（订阅者归零）、新的立刻重建（订阅者回来），中间通常不到 1 秒。若宽限期是 0，每次旋转都会真的断开数据库流再重连，白白浪费一次查询。

判断标准：这个数值应该略大于"界面销毁到重建"的耗时。

2.4 两个真实的坑（都写在你的代码里）

坑一：一次性事件放进 StateFlow，会重放

"保存成功"这种提示是一次性事件，不是一个"持续为真的状态"。塞进 StateFlow：屏幕一旋转，Composable 重建并重新 collect，那个值还在，Toast 又弹一遍。

错误 事件当成状态存

把提示塞进 UiState 字段。界面重建时它还在 → 重复弹出；而且"提示"在业务上根本不是状态。

正解 双通道

状态走 StateFlow（可重放，本来就该重放）；一次性事件走 SharedFlow（发出即消费）。

…/ui/viewmodel/RuleEditorViewModel.kt　（双通道：状态流 + 事件流） KOTLIN 
// 通道 A：持续状态 —— 界面重建后要原样恢复，所以可重放
private val _state = MutableStateFlow(RuleEditorState())
val state: StateFlow<RuleEditorState> = _state

// 通道 B：一次性提示事件（成功/冲突/失败原因），由界面弹 Snackbar
// extraBufferCapacity=4：允许在无人订阅时先攒着，避免 emit 挂起丢失
private val _events = MutableSharedFlow<String>(extraBufferCapacity = 4)
val events: SharedFlow<String> = _events

// 使用处：校验不通过时发事件，而不是改状态
val conflict = findConflict(s.startMinute, s.endMinute)
if (conflict != null) {
    _events.tryEmit(conflict)   // tryEmit：不挂起、不丢事件
    return@launch
}

坑二：ViewModel 感知不到 ON_RESUME

ViewModel 生命周期比 View 长，这是优点；代价是它对"界面回到前台"这件事一无所知——它只有 onCleared()，没有 onResume()。你的项目里正好踩到，解法就写在 HomeScreen.kt：

…/ui/screens/HomeScreen.kt　（由 View 把生命周期事件转发给 ViewModel） KOTLIN 
val lifecycleOwner = LocalLifecycleOwner.current
DisposableEffect(lifecycleOwner) {
    val observer = LifecycleEventObserver { _, event ->
        if (event == Lifecycle.Event.ON_RESUME) {
            vm.refreshExactAlarmStatus()
            // 暖启动（从最近任务/点图标恢复）不走 onCreate，
            // 必须在此重算"当前生效规则"，否则 Hero/生效中标签停留在上次前台时刻的旧状态
            vm.recomputeCurrent()
        }
    }
    lifecycleOwner.lifecycle.addObserver(observer)
    onDispose { lifecycleOwner.lifecycle.removeObserver(observer) }
}
这个坑的通用形态

凡是"从系统设置页返回""从别的 App 切回来"这类场景，ViewModel 都需要被通知。 通用解法：由 View 侧用生命周期观察者把事件转发给 ViewModel。 DisposableEffect 的 onDispose 负责注销——忘了注销就是内存泄漏，这一对必须成对出现。

第三章 · CHAPTER Ⅲ

判据：这段代码该放哪一层

架构知识落到日常，真正的动作只有一个：新建一个函数时，知道它该放在哪个文件。

表 3-1　分层归属判断表（可直接当 checklist 用）
如果这段代码…归属理由 / 本项目实例
读写数据库、网络、文件系统Repository数据源门面，上层不该知道数据从哪来。ScreensaverRepository
纯计算：无 IO、无 Android 框架依赖、输入输出确定domain 纯函数可在 JVM 上直接单测，不需要 Robolectric。ScheduleEngine——你那 15 个单测全压在这一层
要跨界面存活、被多个 UI 读取、要响应事件ViewModel状态宿主。HomeViewModel

需要 Context / 系统服务（AlarmManager、WallpaperManager）系统封装层ViewModel 持 Context 会泄漏。AlarmScheduler / WallpaperApplier——所以它们在根包 scheduler/ 而不在 domain/
把上面这些装配起来、决定谁依赖谁DI 容器手动 DI。AppContainer

3.1 实例解剖：为什么 ScheduleEngine 是 object

app/src/main/java/com/screensaver/domain/scheduler/ScheduleEngine.kt KOTLIN 
/**
 * 调度引擎：纯函数，无 Android 运行时时依赖（操作的是纯 Kotlin 实体），便于单测。
 *
 * 模型（对齐需求/架构文档的"剪开拉直"）：
 *  - 一天 = 0:00 → 24:00 的一条直线，被切成 0..1439 的"当天第几分钟"。
 *  - 一条规则永远不跨午夜（跨午夜由编辑器拆成两条存储），故 endMinute 永远 > startMinute。
 *  - 因此命中判断只有【一种】：start <= now < end，无需任何 wrap-around 分支。
 */
object ScheduleEngine {          // ← object：无状态，天然单例，不需要注入

    fun resolve(
        now: Int,
        rules: List<ScheduleRuleEntity>,
        domain: WallpaperDomain,
    ): ScheduleRuleEntity? {
        return rules.filter {
            it.wallpaperDomain == domain &&
                it.startMinute <= now && now < it.endMinute
        }.minByOrNull { it.startMinute }
    }
}

这段代码里藏着三个可以立刻复用的设计决策：

  1. 用 object 而不是 class无状态的工具用 object，省掉一次依赖注入。判断标准：如果它不需要被替换成假实现来测试，就不必做成可注入的类。
  2. 用"剪开拉直"消灭分支把"一天"建模成 0..1439 的直线，规定规则不跨午夜（跨午夜由编辑器拆成两条存储）。于是命中判断只剩 start <= now < end 一种，不需要任何 wrap-around 分支。
    这是数据建模的威力：约束加在存储层，逻辑层就干净了。
  3. 返回 null 而不是"默认规则"KDoc 写得很明确："若无命中的规则则返回 null —— 调用方据此不干预，保持该域已有壁纸"。用 null 表达"无"这个业务语义，比哨兵值安全得多。
记住这句话

"能算出来的就不要存，能约束在存储层的就不要留给逻辑层。"
你在 Screensaver 里反复做的这两件事（派生状态用 combine、跨午夜在编辑器拆条），就是架构思维的具体形态。

3.2 一个灰色地带（给你练手）

app/src/main/java/com/screensaver/ui/util/TimeFormat.kt KOTLIN 
import java.util.Calendar

/** 分钟数(0..1440) → "HH:MM"（1440 显示为 24:00）。 */
fun formatMinute(minute: Int): String { /* ... */ }   // ← 纯函数

/** 当前"当天第几分钟"。 */
fun nowMinuteOfDay(): Int {                        // ← 不是纯函数！
    val c = Calendar.getInstance()                  //   依赖系统时钟
    return c.get(Calendar.HOUR_OF_DAY) * 60 + c.get(Calendar.MINUTE)
}

注意这个文件在 ui/util/ 下，却被 HomeViewModel 引用。formatMinute() 是纯函数没问题；但 nowMinuteOfDay() 读系统时钟，严格说不是纯函数，却被业务层依赖。

怎么看待这种"灰色地带"

两种处理都成立，关键是你得知道它是灰的：
① 留着——它只依赖 java.util.Calendar 而非 android.*，单测照样能跑，工程上完全可接受；
② 抽出"时钟"接口——把 nowMinuteOfDay() 变成可注入的 Clock，单测时能固定时间（这是消除"时间不确定性"的标准做法，你的 15 个单测若涉及时间边界就会需要它）。

能识别出它是灰色地带，比强行给它分类更重要。架构判断力就长在这种地方。

答案是：它们是三种完全不同的机制，你的项目三种都用上了，而且都用对了地方。

第四章 · CHAPTER Ⅳ

Signals 是什么

它既不是新架构，也不算设计思想。这一章给你它的精确定义、可运行的最小实现，以及它在软件工程层次里的准确位置。

4.1 先拆掉译名的坑：Event ≠ Signal

中文说"信号"，你脑子里浮现的应该是广播、红绿灯、手机信号——"某处发出通知，谁听见谁响应"。但 Signals 恰恰不是这个意思。

表 4-1　Event 与 Signal 的本质区别
Event（事件）Signal（信号）
携带发生了什么当前值是什么
错过错过就没了随时能读到，永远有值
依赖手动 on / off，漏一个就泄漏读一次即自动登记
你的例子ScreenOnReceiver 收到"亮屏了"mutableStateOf 存的"弹窗开不开"

命名来自电子工程：signal = 一个随时间变化的量，沿着导线传给需要它的元件。所以最贴切的类比是——

Signal 是一根带电的导线。
你把灯泡焊上去（读一次），电就来了；电源一变电压，灯泡立刻跟着变；没焊在它上面的元件完全不受影响，连电都不耗。

4.2 精确定义与三个必要特征

定义

Signal 是一个"值的容器"。它在被读取时自动记下"谁在读我"，在被修改时只通知这些记下来的读者。

特征说明缺了会怎样
① 持有值不是"发生了什么"，而是"现在是什么"退化成 Event
② 读即订阅读取时自动登记依赖，无需声明退化成普通变量 + 手动订阅
③ 细粒度通知只通知真正读过它的订阅者退化成"全局广播 + 全量刷新"

4.3 核心机制：读即订阅（含可运行的最小实现）

全部魔法就在三行关键代码里。下面这段 JS 可以直接跑：

signals.js　（极简版 · 已验证可运行） JAVASCRIPT 
let currentObserver = null;        // 全局"当前是谁在读取"的指针

function signal(initial) {
  let value = initial;
  const subscribers = new Set();
  return {
    get() {
      // 关键 1：谁在我被读取时"在场"，谁就是我的订阅者
      if (currentObserver) subscribers.add(currentObserver);
      return value;
    },
    set(next) {
      if (Object.is(next, value)) return;   // 关键 2：值没变就不通知
      value = next;
      for (const sub of [...subscribers]) sub();
    }
  };
}

function effect(fn) {
  const execute = () => {
    currentObserver = execute;              // 关键 3：执行前"亮身份"
    try { fn(); } finally { currentObserver = null; }
  };
  execute();                              // 首次执行 = 建立依赖图
}
用法与输出（实测） JAVASCRIPT 
const count = signal(0);
const show  = signal(true);

effect(() => console.log(show.get() ? `count=${count.get()}` : "hidden"));

// 输出：count=0     ← 首次执行，读到了 show 和 count，两者都登记了

show.set(false);   // 输出：hidden
count.set(1);      // 输出：（见下方说明）
count.set(2);      // 输出：（见下方说明）
show.set(true);    // 输出：count=2
上面那个极简版有个真 bug —— 而且它证明了一件重要的事

注意第一次 show.set(false) 之后，effect 重跑时只读了 show，没读 count。但 count 的订阅表里还留着旧的登记。于是：

实测输出（极简版）：count=0 / hidden / hidden / hidden / count=2 —— count.set(1) 和 set(2) 都误触发了。

修复方式是"双向登记 + 自动清理"：让 observer 也记住自己订阅了哪些 signal，每次重跑前先摘掉旧登记：

signals.js　（完整版：补上自动清理 · 已验证） JAVASCRIPT 
function signal(initial) {
  let value = initial;
  const subscribers = new Set();
  return {
    get() {
      if (currentObserver) {
        subscribers.add(currentObserver);
        currentObserver.deps.add(subscribers);   // ← 双向登记
      }
      return value;
    },
    set(next) { /* 同上 */ }
  };
}

function effect(fn) {
  const execute = () => {
    // 自动清理：重跑前先把自己从所有旧 signal 的订阅表里摘掉
    for (const dep of execute.deps) dep.delete(execute);
    execute.deps.clear();
    currentObserver = execute;
    try { fn(); } finally { currentObserver = null; }
  };
  execute.deps = new Set();
  execute();
}

同一个测试用例的实测输出（完整版）：count=0 / hidden / count=2 —— count.set(1) 和 set(2) 完全静默，符合预期。

这一课的价值

"自动清理"不是性能优化，是正确性要求。只要 effect 里有条件分支（if、三元、早返回），缺了它就会出现"明明不该触发却触发了"的幽灵更新——而且极难排查。

顺带一提：你项目里 DisposableEffect 的 onDispose 在做同样性质的事——虽然机制不同（那是生命周期回调，不是依赖追踪），但背后的原则是同一条：登记与注销必须成对出现。

生产实现还额外做四件事

优化解决什么
Push-Pull 求值信号变了先"标脏"，等真被读时才重算。避免大依赖图里的一连串无谓计算
Glitch-Free同一批次改了 a 和 b，依赖二者的 computed 只算一次，不会中间态闪一下
自动清理见上——正确性要求，不是优化
相等性检查Object.is 相同就不通知——这就是 data class 能帮你省掉重组的原理

4.4 层次定位：Signals 既不是架构，也不算设计思想

这是本章最需要讲清的问题。软件工程里有四个层次：

三个反证：它与架构正交

组合存在吗实例
MVVM + 不用 Signals✅React 19 + Zustand——用 VDOM diff 走完"状态→UI"，照样是标准 MVVM
MVVM + Signals✅Vue + Pinia；你的 Compose + ViewModel
Signals + 不是 MVVM✅所有状态堆在组件里、业务逻辑塞进 computed——照样写出烂架构
Signals + 没有 ViewModel✅状态直接放模块级文件（Svelte 5 Runes 支持 .svelte.js 里写 $state）
一句话

Signals 和 MVVM 是两个正交的维度。就像"用不用钢筋"和"房子是别墅还是公寓"——是两件事，可以自由组合。
所以别再纠结"用了 Signals 是不是就不是 MVVM 了"。

4.5 那它跟架构的关联是什么？只管"状态 → UI"那一段路

MVVM 规定了"事件上行、状态下行"，但一个字都没规定"下行这条路该怎么修"。这段路有三种修法：

表 4-2　"状态 → UI"的三种走法
走法状态变了以后发生什么代价代表
命令式你自己写 textView.text = x漏一处就是 bug，且永远不知道漏了哪上古 MVC

细粒度响应式

Compose

这就是全部关联。Signals 不关心你怎么分层、不关心状态该放哪、不关心业务逻辑写在哪——它只负责把"值变了"这件事，精准送到真正需要它的那一个显示点上。

4.6 一个补充：机制会反作用于架构

虽然 Signals 只是第 3 层的实现细节，但它不是"无副作用的选择"——工具会塑造你写代码的习惯：

Signals 下

派生状态近乎免费（computed 自动缓存 + 惰性重算）→ 你会自然地多用派生、少存状态 → 状态层变薄 → 架构更干净。

而且状态可放在组件外、模块级 → 状态不必困在组件里。

粗粒度 VDOM 下

多一次重渲染有成本，人们倾向于把中间结果缓存进 state → 状态膨胀 → 到处是 useMemo / 依赖数组 → 心智负担。

回看你的代码，这个效应已经发生了：

第五章 · CHAPTER Ⅴ

包到底怎么分

回到第 0 章那个问题。现在你有了判断依据，可以自己做了。

先把话说破

MVVM 只规定逻辑角色（View / ViewModel / Model），一个字都没提目录怎么建。
分包是工程实践，不是架构规范——所以它才有下面这些不同的做法。

5.1 两种主流组织法

表 5-1　按层分 vs 按功能分
按层分（layer-first）按功能分（feature-first）
长相ui/screens/ ui/viewmodel/ domain/ data/feature/home/ feature/editor/ core/domain/
每个功能的代码分散在 4 个包里集中在 1 个包里
适合小项目（功能 < 10 个）中大项目（多人协作、功能多）
优点新手一眼看懂分层在哪改一个功能只开一个目录；删功能直接删文件夹
致命缺点功能一多，screens/ 下堆 50 个文件，且改一个需求要在 4 个目录间来回跳分层约束变弱，容易出现 A feature 直接 import B feature 的内部类
你的项目✅ 就是这个（正确选择）—

你的项目选 layer-first 是对的——只有 2 个界面，feature-first 会变成"每个 feature 包里各放 2 个文件"的形式主义。

判断标准

当"改一个需求要在几个目录间跳"让你开始烦躁时，就该换成 feature-first 了。
拿不准就先按层分——小项目的重构成本极低，别提前设计。

收束 · CLOSING

可带走的三条，与一份自检清单

三条思想

  1. 状态应该活得比 UI 久，且不该由 UI 持有这是 MVVM、Flux、乃至服务端 session 设计的共同底层逻辑。凡是"刷新一下就没了但你希望它还在"的东西，都属于这一层。
  2. 依赖方向要单向，越界的代价要尽量高单向数据流不是为了好看，是为了让"当前界面对不对"变成可推理的纯函数。能下沉到编译器检查的约束（如 StateFlow 对外只读）才是真约束。
  3. 能算的别存，能约束在存储层的别留给逻辑层派生状态用 combine；跨午夜在编辑器拆成两条而不是在引擎里写 wrap-around。复杂度前移到数据模型，后面的代码会成片地变简单。

三条忠告

一 · 判断架构好坏的尺子只有一把

改一个需求，要动几个地方？
你那个"屏保 Tab 新建、默认域却是桌面"的 bug，本质就是状态归属没想清楚——首页的"当前 Tab"没打通到编辑器，只能在层与层之间用参数硬传。
动手画"状态归属表"的时间，永远是值得的。

二 · 别把目录好看当成架构好

每当你想调整包名让它"更清爽"时，先问：我是在改依赖约束，还是在改外观？
如果是后者——停手，去看 import 列表。那里才有真问题。

三 · 别急着重写老项目

为架构纯粹性去返工，性价比通常低于修掉一个真实 bug。
例外只有一种：当架构问题已经在持续产生 bug 时，它就不是纯粹性问题，而是成本问题了。

关于 Signals 的行业现状（一句话带过）
