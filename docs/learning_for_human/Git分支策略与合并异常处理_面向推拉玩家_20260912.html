①重新理解分支：三个指针，不是一个文件夹

只会 push/pull 的人通常有个隐藏误解："建分支 = 把代码复制一份"。错。 分支、tag、HEAD 本质上都是指针——一张 41 字节的便签，内容是"某个提交的编号"。理解了这一点，后面所有概念都会变简单：

指针比喻会不会移动用途
分支 (branch)夹在"最新读到那页"的书签会——你在它上面提交，它自动跟着走标记一条开发线的最新位置
tag盖在某页上的钢印永不移动钉死一个里程碑（"这个状态发过版"）
HEAD"你此刻翻到哪页"的书签随 checkout / commit 移动记录当前所在位置
实战 · 打里程碑 tag
本案例中，功能开发完、双真机验证通过后，我们用附注 tag 钉住这个状态： 
git tag -a v1.1.0 -m "本应用的基本功能已实现，两款真机测试可以正常运行"
git push origin v1.1.0      # ⚠️ tag 不随普通 push 走，必须显式推
三重自证它确实钉对了位置：git log --decorate 看 tag 是否和 HEAD 同提交、 git describe --tags 输出干净的 v1.1.0（无 -1-gxxxx 偏差后缀）、 git rev-parse main 与 git rev-parse v1.1.0^{commit} 哈希相同。
为什么 tag 是新手的救命绳：提交保证代码"丢不了"，但合并之后"我验证过的那个状态"就不再是任何分支的尖端了—— 没有名字，只能去 reflog 里挖。tag 给它一个永久名字：任何时候 git diff v1.1.0 看变化、 git reset --hard v1.1.0 一键回去。

②分支策略：按团队形态选车道模型

策略没有高低，只有匹配。三个真实模型，按协作复杂度递增：

模型 A · 单主干（main only）—— 1~2 人，串行开发

所有人直接在 main 上提交、推送。分支只有一条，心智成本为零。 前提纪律：① 提交说明必须可复盘（类型+目的+范围，拒绝"修复若干BUG"）； ② 配合里程碑 tag 使用——每个"验证过的完整状态"钉一枚，这是单人模型唯一的后悔药。

模型 B · 单主干 + 里程碑 tag —— 双人小队（本案例采用的增强版）

还是只合作战，但每个"编译+测试+真机全通过"的阶段性状态打一枚 tag。 合并同事代码、做大改动之前，tag 就是书签和后悔药：先钉后动。

模型 C · 短命特性分支 —— 3 人以上 / 多任务并行

每个任务开 feature/主题 分支，完成后合回 main 并删除分支。 适合"多人同时改、互不想踩"的场景。代价：分支管理成本 + 合并频率上升。 两人小队早期上这套属于过度设计。
你的处境推荐模型关键纪律
1 人，自用项目A：单主干提交说明可复盘
2 人，偶有并行B：单主干 + 里程碑 tag大动作前先钉 tag；合并前先 fetch 看牌
3 人+ / 多任务并行C：短命特性分支分支完成即合并删除，防堆积
任何模型通用的红线：未提交 = 不设防。本案例中两次"文件消失"事故，损失的都是在工作区裸奔、 从未 commit 的文档——结论性文档写完 30 秒内就 add + commit，这是 1 换 100 的习惯。

③合并的真实机制：三方合并，行块级取并集

很多人以为"合并 = 两边文件不一样的都要人裁决"。错。Git 的合并是三方对比： 它先找到两条线的共同祖先，然后问三个问题——祖先→你 改了什么？祖先→他 改了什么？ 再按行块（hunk）级别逐块处理：

"Among the changes made to the common ancestor's version, non-overlapping ones are incorporated in the final result verbatim. When both sides made changes to the same area, however, Git cannot randomly pick one side over the other, and asks you to resolve it." —— git-scm.com/docs/git-merge · HOW CONFLICTS ARE PRESENTED

所以正确的理解是三句话：

  1. 单边改动直接采用——包括新增文件、修改、甚至删除（一边删了、另一边没动过，结果就是没了，这不是并集）
  2. 双边改动按行块取并集——改了同一个文件的不同区域，自动融合，无感完成
  3. 只有同一行区域两边都改——才标 <<<<<<< 冲突标记，停下交给人
最重要的警告：没冲突 ≠ 结果正确。
真实案例：我和同事都给 HomeViewModel 加了 batteryWhitelisted 状态。 如果他加在文件头部、我加在尾部——不同行块，Git 会把两段都融进去，一个类里出现两套同名状态。 运气差直接编译报错（还算幸运）；运气好名字错开 → 编译通过但逻辑打架。 这就是"编译过了但逻辑错了"的根源：自动合并保证的是文本融合成功，不保证语义正确。 两边改过同一批文件时，即使零冲突也要人工过一遍。

④合并异常处理机制：六个异常 + 红线清单

异常 ① push 被拒：non-fast-forward（最高发）

症状：git push 被拒，提示 non-fast-forward。
原因：远程分支上站着你本地没有的提交（你和同事从同一点分头走了）。此时接受你的推送 = 把远程已有的提交抹掉，官方原话：
"The command by default does not allow an update that is not a fast-forward to prevent such loss of history." —— git-scm.com/docs/git-push · NOTE ABOUT FAST-FORWARDS
它是保护，不是故障。三条出路：
出路效果适用
merge 接回两条线合并提交把双方历史正式连起来，远程快进✅ 共享分支的默认正解
rebase 重排自己的提交把你的提交搬到对方线上⚠️ 未推送过的私人提交可用
--force 强推无视检查，覆盖远程❌ 见下方红线
红线：共享分支禁止 force push。官方文档的原文就叫这个性质——
"blindly pushing with --force will lose their work"（盲目强推会丢掉别人的工作） / "It can cause the remote repository to lose commits; use it with care." —— git-scm.com/docs/git-push
force push 后，同事的提交从共享分支上"蒸发"，他本地仓库与远程彻底打架，且极难追溯。

异常 ② 冲突现场：不是"挑一个"，是核对双方意图

冲突标记 <<<<<<< 你的版本 ======= 他的版本 >>>>>>> 出现时，对每个冲突问三个问题： ①这个冲突为什么产生？②两边各想做什么？③合并后的行为符合预期吗？ 两边真的一个字不差 → 取谁都一样；思路同细节不同 → 逐块裁决，必要时找对方对齐口径。 裁决完 git add + git commit 完成合并。 禁止无脑选 ours / theirs——那等于把裁决丢给硬币。

异常 ③ 合并到一半反悔

git merge --abort        # 回到合并开始前的状态
官方警告："Running git merge with non-trivial uncommitted changes is discouraged." —— 合并前有未提交改动时，--abort 可能无法完全恢复。所以铁律是：先提交，再合并。 —— git-scm.com/docs/git-merge · OPTIONS --abort

异常 ④ 合并完成但整体否定

git reset --hard ORIG_HEAD    # ORIG_HEAD = 合并前 main 的位置，Git 自动记录
git reset --hard v1.1.0       # 或回到你钉过的里程碑 tag

破坏性命令，但正因为合并前钉过 tag / 打过书签，才敢用。

异常 ⑤ 未跟踪文件挡道（Untracked Files Preventing Checkout）

真实案例
切分支时被拒："untracked files will be overwritten by checkout: gradlew, gradle/wrapper/…"。
机理：目标分支对这几个路径有正式版本要写入工作区，而工作区同路径占着不在任何提交里的未跟踪文件—— 覆盖即真丢失，Git 拒绝静默覆盖。修复：确认未跟踪副本是垃圾（或已留档）后删掉，切回时正式版本自动回来。
本案例的额外教训：那份"再生"的 gradle-wrapper.properties 指向 Gradle 9.3.0，而项目要 8.9—— 工具自动再生的文件 ≠ 正主版本，删之前先看一眼内容。

异常 ⑥ 终极兜底：reflog

只要提交过，对象就永久在库里——分支指针丢了、合并搞砸了、分支删了，都能从 git reflog 按时间线找回，git reset --hard <hash> 复位。 反过来推论：没提交过的东西（未跟踪文件）没有任何保险——连 reflog 都救不了它。

特殊武器：-s ours 策略合并 —— 内容独走，历史接回

场景：同事的方案被评审否决，但他的提交已在远程 main 上，你的推送被 non-fast-forward 拒绝。 你想要"远程最终内容 100% 是我的"，又不肯 force push。答案： 
git merge -s ours colleague-fix   # 合并提交把对方接入祖先，内容树 100% 取当前分支
"the resulting tree of the merge is always that of the current branch head, effectively ignoring all changes from all other branches. It is meant to supersede old development history of side branches." —— git-scm.com/docs/git-merge · MERGE STRATEGIES（注意：与 -X ours 选项完全不同）
效果：内容上 main 独自前进（对方代码零进入），拓扑上两条线正式握手（对方提交成为祖先，push 畅通）， 对方的工作在历史里可查可取回（git show <commit>:<路径>）。 合并说明必须写明裁决依据——这是"方案裁决"与"悄悄覆盖"的分界线。

⑤实战复盘：同 bug 双方案撞车全流程

完整背景：远程 main 上有同事的 bug 修复提交；我在本地独立做了同 bug 的另一版修复，且已双真机验证。决策全流程：

本次案例沉淀的四条教训

  1. 先审后合：fetch + log + show + diff --stat，看清再合——blind pull 是新手的头号事故源
  2. 先钉后动：验证过的状态先打 tag，合并/大改之前它是唯一的后悔药
  3. 裁决要留痕：为什么取谁的方案、依据什么测试证据，写进合并提交说明——三个月后复盘全靠它
  4. 沟通带证据：否决同事的方案 ≠ 否定同事；对比文档 + 测试数据先行，他的提交永远在历史里可取回

⑥命令速查卡

场景命令
看远程发生了什么（不动工作区）git fetch origin → git log main..origin/main --oneline
看某个提交改了什么git show <hash>
预判合并会撞哪些文件git diff main...origin/main --stat
钉里程碑git tag -a v1.1.0 -m "说明" → git push origin v1.1.0
对比任意状态git diff v1.1.0 --stat
冲突到一半弃权git merge --abort
合并后整体否定git reset --hard ORIG_HEAD 或 git reset --hard v1.1.0
内容全取我方的策略合并git merge -s ours <branch>
找回"丢失"的提交git reflog → git reset --hard <hash>
取回历史中某个版本的文件git show <commit>:<路径>
红线清单（违反任何一条都可能造成协作事故）
  • 共享分支禁止 push --force（官方警告：会丢掉别人的工作）
  • 有未提交改动时不要 merge / 切分支（官方警告 --abort 可能无法完全恢复）
  • 不用 stash 当保险——重要内容宁可提交或复制备份
  • 冲突不盲选 ours / theirs，逐块核对双方意图
  • 结论性文档写完立即 commit——未跟踪 = 不设防
结语：git 的所有"异常"，几乎都是保护机制在正确地拦住你： non-fast-forward 在保护远程的历史，checkout 拒绝在保护未跟踪的文件，冲突标记在保护双方的意图。 看懂它在保护什么，恐惧就变成了流程。
