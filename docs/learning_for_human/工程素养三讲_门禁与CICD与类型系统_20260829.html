00 / PROLOGUE

写在前面：这三讲是一根线上的三个结

不要把它们当成三个孤立名词背下来。

如果只看字面，门禁讲的是流程，CI/CD讲的是工具链，类型系统讲的是语言设计—— 三者风马牛不相及。但它们回答的是同一个问题：

「一个缺陷，最早可以在什么时候、被谁、用什么方式拦下来？」

门禁回答「在哪个关卡拦」，CI/CD 回答「谁去自动执行这个关卡」，类型系统回答「编译器能替你拦掉多少」。

所以这份教材的阅读顺序是有讲究的：先看门禁（建立"关卡思维"）， 再看CI/CD（看关卡如何被自动化），最后看类型系统（看最左端那道关——编译器——到底能做什么、不能做什么）。

① 文中带 官方 标记的引文，均逐字取自官方或权威一手文档 （JetBrains / OpenJDK / Python 官方 / MDN / GitHub Docs / GitLab Docs / SonarSource / PEP），英文原文照录。 社区 标记的是社区、百科或教材整理，只用于补充时间线与背景，不作为定义依据。

01 / GATE

门禁：不达标，就禁止通行

Quality Gate · Stage-Gate · Merge Gate

1.1一句话定义

门禁（Gate）是一道硬性检查关卡：流程或代码走到这里，必须先满足一组预先写死的标准， 达标才放行，不达标就卡住。它的本质是把"质量要求"从事后救火变成事前卡点。

英文文档里你会撞见三种叫法，它们不是同义词，来源完全不同——这是最容易混淆的地方：

叫法出处卡在什么位置不达标的后果
阶段门 / Stage-Gate项目管理
（新产品开发流程）		项目阶段之间
需求→设计→开发→测试→发布		阶段不得推进；产出 Go / Kill / Hold / Recycle 四种决策
质量门禁 / Quality Gate代码分析与 CI/CD
（SonarQube 等）		每次提交 / PR / 发布前流水线失败，自动阻断合并或部署
合并门禁 / Merge Gate代码托管平台
（GitHub / GitLab 分支保护）		PR 合入受保护分支之前合并按钮不可用，必须补齐审批或状态检查

1.2两类门禁：一张图看清分野

1.3阶段门的来历：这不是软件行业发明的

这一点常被忽略："分阶段 + 阶段间设决策点"的思路，最早来自重资产的采购与工程管理，不是软件业。

  • 1970 年代：NASA 与美国国防部在航天 / 国防采购中采用分阶段评审（如 NASA 1972 年的 NHB 7121.2 文档）， 逻辑是"把高风险的大笔资金拆成几段，每段结束拿证据来换下一段的钱"。社区
  • 1980 年代：Robert G. Cooper 基于对数十家企业新产品的实证研究，把这套逻辑搬进商业新产品开发， 建立了著名的 Stage-Gate®。术语 "stage-gate" 首次出现于他 1988 年发表在 Journal of Marketing Management 的论文；更早版本已见于其 1986 年著作 Winning at New Products。社区
  • 1990 年代以后：CMMI 的里程碑评审、华为 IPD 体系的 DCP（决策评审点），都是这条血脉在研发组织里的落地形态。

产品开发与管理协会（PDMA）将 Stage-Gate 定义为——"把开发工作切分为按时间排序的若干阶段， 阶段之间由管理决策门隔开"的一种流程。

社区 转引 PDMA 对 Stage-Gate 的定义 · 见附录 A-3

◆ 为什么要知道这个来历

因为门的设计感来自"资本支出决策"，不是"技术检查"。这解释了为什么阶段门的标准写得像 准入清单（有没有商业论证、财务测算、风险评估），而不是像单测覆盖率。 如果你把阶段门当技术评审来开，就跑偏了。

1.4一道门里到底装什么：三件套

Cooper 对 Gate 的经典拆解是三样东西，缺一样这道门就是走过场：

① 交付物 Deliverables

团队必须在门前交出来的东西，是看得见、可核对的成果。
例：需求规格说明书、架构设计文档、测试用例集

② 标准 Criteria

衡量交付物的尺子，通常在上一道门就提前定好，不能临门改标准。
例：需求评审通过、架构签字、无阻塞缺陷

③ 产出 Output

门的决策结果：Go / Kill / Hold / Recycle，以及对下一阶段的资源承诺（人、钱、时间）。

⚑ 一句话判断你的门是不是真的门

如果过去一年里，你所在的流程从来没有 Kill 掉任何一个项目或需求， 那说明你只有 Stage，没有 Gate。这是阶段门最常见的失效模式。

1.5质量门禁长什么样：以 SonarQube 为例

流程门靠人评审，质量门靠机器算指标。SonarSource 官方给的定义是：

"Quality gates enforce a quality policy for the results of code review and analysis in your organization by answering one question: is my project ready for release?"

质量门禁通过回答一个问题来落地组织的质量政策：我的项目可以发布了吗？

官方 SonarQube Server Documentation — Understanding quality gates

它的机制极其朴素：一条条件 = 指标 + 比较运算符 + 阈值。任一条件命中，整道门就失败。

// 一条条件的构成（官方示例）
Metric             : Blocker issue      ← 指标：严重阻塞级问题数
Comparison operator : >                 ← 运算符：大于
Error value         : 0                 ← 阈值：0

→ 读作："不允许存在任何 Blocker 级问题"。命中即 Quality Gate FAILED。

官方内置的「Sonar way」门禁只有四条，全部针对新增代码（New Code）：

① 不引入新问题

No new issues are introduced

② 安全热点全部已复核

All new Security Hotspots are reviewed

③ 新代码测试覆盖率 ≥ 80.0%

New code test coverage ≥ 80.0%

④ 新代码重复率 ≤ 3.0%

Duplication in new code ≤ 3.0%

◆ 这里藏着一个非常值得抄回家的设计哲学

门禁只看新代码，不看存量代码。官方的原话精神是："把高标准立在新代码上， 你就不必担心要去满足旧代码的标准、替别人擦屁股。" 反面教材是给存量代码设 Overall Coverage > 80%——老项目一旦挂上这条，流水线会永久红， 团队只能集体忽略门禁，门禁就此死亡。

最关键的一句，它把质量门和"拦截"直接绑在一起：

"It can be used to block the merge of the pull request if the quality gate fails."

如果质量门禁失败，它可以用来阻断该 PR 的合并。

官方 SonarQube Server Documentation — Understanding quality gates

1.6合并门禁：平台层的那把锁

质量门是"算出结果"，合并门是"执行拦截"。GitHub 官方对分支保护规则的描述是：

"You can create a branch protection rule to enforce certain workflows for one or more branches, such as requiring an approving review or passing status checks for all pull requests merged into the protected branch."

你可以创建分支保护规则，为合并进受保护分支的所有 PR 强制要求"审批通过"或"状态检查通过"。

官方 GitHub Docs — Managing a branch protection rule

常见的合并门禁开关（对应官方设置项英文原名）：

  • Require a pull request before merging —— 禁止直接 push 到主干
  • Require approvals —— 至少 N 人审批
  • Require status checks to pass before merging —— CI 必须全绿（这就是 CI/CD 与门禁的焊接点）
  • Require review from Code Owners —— 指定目录必须由对应负责人审
  • Require branches to be up to date before merging —— 合并前必须先同步主干

1.7门禁的三种死法

死法一：过严

门太多、阈值太狠 → 交付变慢 → 团队想办法绕过去。门禁要少而准：先立 3 条，跑顺了再加。

死法二：形同虚设

标准设了不执行：Approve 随便点、红灯照样合并。一旦有人发现红灯能过，这道门当场失效。

死法三：当 KPI 用

门禁是质量护栏，不是考核工具。一旦用它卡人绩效，上报的数据立刻失真。

02 / CI · CD

CI/CD：把关卡装进自动流水线

为什么这个词永远在你提 PR 的时候跳出来？

2.1因为"合并到主干"就是那条扳机

现代团队的默认约定是：main / master 是受保护分支， 任何人都不能直接 push，必须走 PR / MR。而托管平台会在"这个 PR 要合并"的时刻自动触发流水线去跑构建和测试； 同时"必须 CI 全绿"又被设成了合并门禁。于是你每次提合并，背后都有一整条流水线在跑——这就是它总在合并场景被提起的原因。

2.2CI 的权威定义：注意"每天"这个关键词

"Continuous Integration is a software development practice where each member of a team merges their changes into a codebase together with their colleagues changes at least daily. Each of these integrations is verified by an automated build (including test) to detect integration errors as quickly as possible."

持续集成是一种软件开发实践：团队每个成员至少每天把自己改动与同事的改动合并进同一代码库； 每一次集成都由自动化构建（含测试）验证，以便尽快发现集成错误。

官方 Martin Fowler，Continuous Integration（2001 年首写，2023 年重写）

把这句话拆成两个可检查的条件，缺一不可：

条件 A · 频率

每人至少每天合入主干一次。憋一周才合一个大分支，那不叫 CI——Fowler 管那叫"那个令人沮丧的仓库"。

条件 B · 自动验证

每次集成必须跑自动化构建 + 测试。没有自动验证的频繁合并，只是高频地制造混乱。

⚑ 一个高频误判

"我们装了 Jenkins / 配了 GitHub Actions" 不等于 在做 CI。 Fowler 原文明说：很多人声称自己在做 CI，但一描述工作流就发现缺了关键部分。 判据永远是上面两条，不是那台服务器。

2.3两个 CD：交付（人点按钮）vs 部署（自己发）

CI 解决"合并不出问题"，CD 解决"发布不费人力"。两个 CD 常被混为一谈，区别只有一句： 交付 = 人点一下才发；部署 = 门禁过了自己发。

Fowler 给"你算不算在做持续交付"的四条判据（可直接当自检清单用）：

"You're doing continuous delivery when: [1] Your software is deployable throughout its lifecycle · [2] Your team prioritizes keeping the software deployable over working on new features · [3] Anybody can get fast, automated feedback on the production readiness of their systems any time somebody makes a change to them · [4] You can perform push-button deployments of any version of the software to any environment on demand."

官方 Martin Fowler，bliki — Continuous Delivery

2.4流水线的零件：四个名词一次分清

GitLab 官方给的整体定义与最小模型，是最清晰的入门表述：

"CI/CD is a continuous method of software development, where you continuously build, test, deploy, and monitor iterative code changes."

CI/CD 是一种持续进行的软件开发方法：你持续地构建、测试、部署并监控迭代式的代码变更。

官方 GitLab Docs — Get started with GitLab CI/CD

Pipeline 流水线

一次完整执行。由 commit / MR / 定时任务 / 手动触发而创建。

Stage 阶段

定义执行顺序。典型：build → test → deploy。

Job 作业

阶段里的具体任务，如"编译代码""跑测试"。真正干活的单元。

Runner 执行器

跑 job 的代理程序，装在机器或容器上。它拉代码、装环境、执行脚本。

2.5门禁 与 CI/CD：容器与内容的关系

这是把第一讲和第二讲缝起来的那一针：

  • CI/CD 是管道和引擎——谁在跑、跑什么、跑完去哪。
  • 门禁是管道里的关卡——跑到某一步必须达标，否则卡住。

所以这两个词总成对出现：CI/CD 负责自动化执行，门禁负责定义什么算过关。 图 2 里的三个菱形，既是流水线的节点，也是门禁的实例——同一件事的两种说法。

2.6左移 Shift-Left：门禁思想的源头口号

这个 2001 年由 Larry Smith 在 Dr. Dobb's Journal 提出的词，是"门禁"这种做法的意识形态来源：

"Shift-left testing is how I refer to a better way of integrating the quality assurance (QA) and development parts of a software project."

左移测试，是我对"把质量保证与开发更好地融合在一起"这种做法的叫法。

社区 Larry Smith，Dr. Dobb's Journal（2001）· 术语公认出处

为什么叫"左"？因为流程图习惯从左到右：需求、设计、编码在左，测试、预发、生产在右。 把测试往左挪，就是在图上把一个方框从右推到左。背后的经济学很硬： 设计阶段发现一个缺陷，改几行字；生产环境发现同一个缺陷，是一次事故。

◆ 类型系统是"最左"的那道门禁

顺着这条线往下想：编译器在你按下 Run 的那一刻（甚至打字的时候）就拦下一批错误—— 这比任何 CI 流水线都更靠左。这就是第三讲要讲的东西。

03 / TYPE SYSTEM

类型系统：最靠左的那道自动门禁

为什么 Kotlin 排除了语法错误，点 Run 还是会报红？

3.1从一个真实困惑出发

💬 原始问题

"写 Python 时，保证静态状态下没语法错误，直接运行即可；之后就算报错也是终端报错，代码不会报红。 而 Kotlin 即使排除了静态状态下的语法错误，点击 Run，还有可能出现新的报红。这是否和 Kotlin 的语言特性有关？"

答案：是的，而且这正是静态类型 + 编译型语言的典型特征。下面把它拆开。

3.2错误暴露的时机：一张时间轴

先纠正一个细节：Python 并非"运行前完全不检查"。CPython 会先把源码编译成字节码， 纯语法错误（SyntaxError）在运行前就会抛。真正被推到运行时的，是类型、属性、未定义名字这类问题—— 而且只有执行到那一行才爆。

◆ 顺带解释"为什么刚才明明没红，点 Run 才红"

Android Studio 编辑器的红线是轻量、局部的检查；而许多跨模块、跨文件的编译错误， 要等 Gradle 跑全量构建时才暴露。所以"点 Run 才红"不是编辑器失灵， 而是浅层检查与全量编译之间的能力差。

3.3静态 vs 动态：什么时候查类型

这一组区分的是检查发生的时机，判据非常干净：

静态类型 Static Typing动态类型 Dynamic Typing
检查时机编译期（运行之前）运行期
类型绑在谁身上绑在变量 / 表达式上绑在值上（变量只是名字）
变量能否换类型不能。声明即定死能。x = 1 后 x = "a" 合法
典型代价要等编译；类型不匹配直接构建失败类型错误可能潜伏到上线，只有执行到才爆
代表Kotlin / Java / C# / Go / Rust / Swift / C++Python / JavaScript / Ruby / PHP / Lua

Python 官方设计 FAQ 的对照表述（注意其措辞是 use static types / uses dynamic types）：

"Other languages, such as Object Pascal, Delphi, and C++, use static types, so it's possible to know, in an unambiguous way, what member is being assigned to. This is the main point of static typing – the compiler always knows the scope of every variable at compile time. Python uses dynamic types. It is impossible to know in advance which attribute will be referenced at runtime."

官方 Python 3 官方文档 — Design and History FAQ

3.4强 vs 弱：允不允许"偷偷帮你转类型"

这一组区分的是混合类型运算时语言的态度：是拒绝并报错，还是悄悄做隐式转换。 MDN 对 JavaScript 的描述是教科书级别的清晰：

"JavaScript is also a weakly typed language, which means it allows implicit type conversion when an operation involves mismatched types, instead of throwing type errors."

JavaScript 也是一门弱类型语言，这意味着当运算涉及不匹配的类型时，它允许隐式类型转换，而不是抛出类型错误。

官方 MDN — JavaScript data types and data structures

// 弱类型的代价：下面四个都是 JS 里真实会发生的求值
1 + "2"        // → "12"    数字被隐式转成字符串，然后拼接
1 - "2"        // → -1      同一对类型，换了个运算符，又转回数字
[] == false   // → true    空数组 → "" → 0，false → 0，于是"相等"
null + 1       // → 1       null 被当作 0 参与算术

// 对照 Python（不替你转）：
1 + "2"        // → TypeError: unsupported operand type(s)

⚠ 重要陷阱：「强 / 弱」没有统一定义

这是本讲最需要记住的一条元知识。与"静态 / 动态"有清晰判据不同， "强类型""弱类型"在学术界没有公认定义。《Types and Programming Languages》作者 Benjamin C. Pierce 说过：

"我花了几个星期……试着弄清楚『强类型』『静态类型』『安全』等术语，但我发现这异常的困难……这些术语的用法不尽相同，所以也就近乎无用。"

社区 中译见附录 A-11。Virginia Tech 的开放教材 OpenDSA 同样明确建议："你应该避免使用 strongly typed / weakly typed 这两个说法，因为它们没有普遍公认的定义。"

实践建议：在技术讨论中，把"它是强类型吗"换成三个可验证的具体问题—— 「是否允许隐式转换？」「能否绕过类型系统？」「类型错误的检查发生在编译期还是运行期？」。 前三个有确定答案，最后一个"强不强"没有。

⚑ 对之前对话的一处更正

我在对话中曾把"Python 是强类型"当作官方结论给出。逐条核查后需要更正： Python 官方文档（含 Design and History FAQ）从未用 "strongly typed" 描述 Python，只有 Python uses dynamic types。 把 Python 归入"动态 + 强"是社区通行归类——依据是不做隐式数值/字符串转换（1 + "2" 抛 TypeError）。 方向没错，但不能挂"官方"标签。这也正好演示了为什么"强/弱"要慎用。

3.7类型推断 ≠ 动态类型：这是最普遍的误解

Kotlin 的 val x = 42 看起来和 Python 的 x = 42 一模一样，但机制完全不同：

// Kotlin：推断出来的是"编译期就定死的静态类型"
val x = 42          // 编译器当场推断 x : Int，此后永远不能再装别的类型
x = "abc"            // ✗ 编译错误：type mismatch（这就是"点 Run 才报红"的一类）

val d: Int          // 先声明、后赋值时，推断无从下手，必须手写类型
d = 10

Kotlin 官方文档对推断与"何时必须手写"的表述：

"Kotlin supports type inference and automatically identifies the data type of a declared variable. When declaring a variable, you can omit the type after the variable name."

"You can use variables only after initializing them. ...you must specify the data type [if you declare first and initialize later]."

官方 Kotlin Documentation — Basic syntax

Python · 动态

x = 42
变量名只是贴在值上的标签，换值时标签跟着换。类型在运行期随值走。

Kotlin · 静态 + 推断

val x = 42
编译器在编译期把 x 定为 Int 并写死。省的是你打字，不是检查。

Java · 静态 + 局部推断

var x = 42;
仅局部变量可推断，字段/参数/返回值仍要显式写。类型同样编译期固定。

OpenJDK 的 JEP 286 FAQ 把这件事说得斩钉截铁：

"Is this dynamic typing? No! Variables are still statically typed, as they have always been. What's happening here is that you have the opportunity to let the compiler figure out the type, rather than typing it out -- but the variable still has a fixed static type."

这是动态类型吗？不是！变量仍然是静态类型的，一如既往。区别在于你让编译器去推算类型、而不是自己把它敲出来——但这个变量依然有一个固定的静态类型。

官方 FAQ for JEP 286 (Local Variable Type Inference)，Brian Goetz / OpenJDK

3.8Kotlin 独有的一道编译期红线：空安全

这是 Kotlin 相较 Java 多出来的一类"点 Run 才红"，也是最值得单独讲的一条。 语言规范里的说法是：

"The type system of Kotlin distinguishes at compile time between nullable and non-nullable types, achieving null-safety, i.e., guaranteeing the absence of runtime errors caused by the absence of value (i.e., null value)."

Kotlin 的类型系统在编译期区分可空与非空类型，从而实现空安全——即保证不会出现"因为值缺失（null）而引发的运行时错误"。

官方 Kotlin language specification — Introduction

所以在 Kotlin 里，一条 String 和一条 String? 是两个不同的类型，不能互相隐式赋值。 这也是为什么你在 Android Studio 里会看到 only safe (?.) or non-null asserted (!!.) calls are allowed 这类报错——它不是啰嗦，是编译器在替你挡 NPE。

项目负责人视角：不同语言，审查重点不同

顺着语言的特长来管，而不是拿同一把尺子量所有代码

核心原则一句话：机器已经替你兜住的部分，就不要再让人花时间查；把人力投在机器查不了的地方。

语言类型编译器 / 工具已替你兜住人工审查与卡点应该重点放在哪
静态 + 强
Kotlin / Java / Go / Rust		 类型不匹配、空安全、未定义引用、可达性、部分并发误用（Rust 尤其多） ① 架构与设计决策
② 并发与线程安全、生命周期、性能
③ 可读性、命名与边界条件

动态 + 强

② 类型注解 + mypy / Pyright 静态检查（把静态护栏补回来）
③ 运行时校验：pydantic 等在数据入口做契约检查
④ 审查时反复追问"这个变量到这儿到底是什么类型"

② 上 TypeScript，把隐式转换入口封死
③ 显式处理 null / undefined 的语义差别

◆ 可落地的三条管理结论

① 静态类型语言的门禁可以自动化得更彻底。直接把"编译通过 + 测试通过 + 质量门禁"设成合并卡点， 编译器就是第一道闸，成本几乎为零。
② 动态/弱类型语言更依赖人工评审与测试。如果团队用 Python / JS，优先推动 mypy / TypeScript 这类渐进式静态检查——这是行业最佳实践，等于把静态语言的护栏补回来。
③ 审查重点永远要说清楚：静态语言少查"类型对不对"，多查"设计对不对"； 动态语言必须多查"类型假设对不对"。

4.1一个务实的补充：渐进式静态化是可选项，不是信仰

给 Python 加类型提示，不代表 Python 变成了静态语言。PEP 484 的态度非常明确：

"It should also be emphasized that Python will remain a dynamically typed language, and the authors have no desire to ever make type hints mandatory, even by convention."

需要强调的是：Python 仍将是一门动态类型语言，作者也绝无意让类型提示成为强制要求，哪怕是约定俗成的强制。

"...no type checking happens at runtime. Instead, the proposal assumes the existence of a separate off-line type checker which users can run over their source code voluntarily."

运行时不做任何类型检查；这个提案假定存在一个独立的离线类型检查器（如 mypy），用户自愿运行它。

官方 PEP 484 — Type Hints

这带来一个管理者必须知道的边界：类型注解是给检查器和 IDE 看的，不是给解释器看的。 所以光写注解没用，必须把 mypy 接进 CI，它才真正成为一道门禁——否则它只是一份可能过期的注释。

05 / ACTION

落地清单：从"知道"到"装上"

先做最小的那一步，别一上来搭全套体系

5.1最小可行的门禁集（三条就够）

不管是个人项目还是小团队，先立这三条，它们的投入产出比最高：

  1. 受保护分支：main 禁止直接 push，一切改动走 PR。
    成本：5 分钟。收益：主干永远有人审过。
  2. 编译 + 测试门禁：PR 触发 CI 跑 assembleDebug 与单元测试， 并设为 Require status checks to pass before merging。
    成本：一个 workflow 文件。收益：挡掉"在我机器上能编"类事故。
  3. 新代码质量门禁：只针对新增代码设阈值（覆盖率、严重问题数）， 绝不对存量代码设硬门槛（见 1.5 节的 Sonar 哲学）。
    成本：一次配置。收益：代码质量只升不降，且不引发"永久红灯"。

⚑ 顺序很重要

先做第 1、2 条并稳定运行两周，再考虑第 3 条。 一次性上全套门禁的典型结局是：流水线天天红 → 团队集体忽略 → 三道门一起死。

5.2可直接用的 Android / Kotlin 工作流

# .github/workflows/ci.yml —— 存到仓库即可生效
name: CI

on:
  pull_request:
    branches: [ main ]      # 提 PR 到 main 时触发（对应图 2 的扳机）
  push:
    branches: [ main ]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up JDK
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'        # Android Gradle Plugin 8.x 需要 JDK 17+

      - name: Grant execute permission for gradlew
        run: chmod +x ./gradlew

      - name: Build debug APK          # ← 门禁 1：编译必须通过
        run: ./gradlew assembleDebug

      - name: Run unit tests           # ← 门禁 2：测试必须全绿
        run: ./gradlew testDebugUnitTest

      - name: Lint                     # ← 门禁 3：静态检查无 error
        run: ./gradlew lintDebug

◆ 配完之后还有一步，别漏

到仓库 Settings → Branches → Add rule，勾上 Require status checks to pass before merging，并选中上面这些 job。 没有这一步，CI 只是个"通知"，不是"门禁"——红了照样能合并。

5.3把三讲映射回你的 Screensaver 项目

你现在的工作流其实已经在用门禁思维，只是没有这么叫它：

现有环节相当于哪类门禁准入标准（建议写成可勾选的清单）
project-manager 输出需求文档阶段门（需求门）PRD 完成、范围冻结、验收标准可测

真机验证最右端的门禁启动只过渡一次、闹钟到点换壁纸、已录规则未丢

◆ 下一步最值得做的一件事

给你的 ScheduleEngine 补一组纯函数单测（覆盖 start ≤ now < end 与 24:00 边界）， 然后按 5.2 把它接进 CI。它同时命中两讲：类型系统让这些测试容易写（纯函数、无副作用）， CI 让它们每次合并自动跑。这是投入最小、收益最实的一步。
